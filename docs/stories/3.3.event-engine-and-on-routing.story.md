# Story 3.3: Event Engine — EventManager + ShantillyEvent + on: como pipeline único

## Story

Como um autor de aplicações no Runtime TUI Declarativo,
Eu quero que todos os eventos relevantes da UI, do ScriptRunner e da Modal Stack sejam normalizados em `ShantillyEvent` e roteados exclusivamente pelo `EventManager` usando o bloco declarativo `on:`,
Para que a lógica de automação seja centralizada, rastreável, segura e desacoplada da implementação de layout e componentes.

## Acceptance Criteria

1. AC1: Todos os eventos relevantes do runtime (UI, scripts, modais, sistema) DEVEM ser representados por `ShantillyEvent` (SourceComponentID, Type, Payload), conforme docs/architecture/data-models.md#5-shantillyevent-e13--tipo-de-evento-normalizado.
2. AC2: O `EventManager` DEVEM ser implementado como roteador único em `internal/runtime/event/...`, consumindo `ShantillyEvent` e a lista `OnHandler` (`AppConfig.On`) para decidir ações.
3. AC3: O bloco `on:` (`[]OnHandler`) DEVE ser utilizado como única fonte declarativa de automação:
   - `Event` obrigatório mapeando para `component_id:type` (ex.: `menu:select`, `deploy_button:click`, `user_form:submit`).
   - Ações permitidas: `RunAction`, `OpenModal` (ModalRequest), `UpdateState` declarativo.
4. AC4: É proibida qualquer lógica reativa “solta” fora do pipeline:
   - `Component`/`LayoutManager`/`ScriptRunner`/Modal Stack não podem chamar scripts diretamente ou aplicar lógica condicional fora de `on:`.
   - Handlers de eventos espalhados no código, não mediados por `EventManager` + `on:`, DEVEM ser considerados violação.
5. AC5: O `EventManager` NÃO executa scripts:
   - Toda execução DEVE ser delegada ao `ScriptRunner` via contratos claros (ex.: `RunAction` → `RunRequest`).
6. AC6: O fluxo mínimo E2E DEVE estar definido:
   - `ShantillyComponent` → emite ShantillyEvent → `EventManager` → encontra OnHandler → dispara ação declarativa:
     - `run:` → ScriptRunner,
     - `open_modal` → Modal Stack,
     - `update_state` → estado declarativo/foco/layout conforme regras.
7. AC7: Ordem de avaliação DEVE ser determinística:
   - OnHandlers avaliados na ordem declarada no YAML.
   - Comportamento para múltiplos OnHandlers para o mesmo `event` documentado (baseline: permitir múltiplos, todos declarativos).
8. AC8: Todos os contratos E1.3 DEVEM ser rastreáveis:
   - Stories E1.3 → docs/architecture (data-models, components, core-workflows) → `internal/runtime/event/...` → QA Matrix E1.3 → Gate `1.x.event-engine.yml`.

  - [ ] Evento de UI:
    - Exemplo: `menu` (list) emite `menu:select` → on: → `run:` para ScriptRunner.
  - [ ] Evento de submissão:
    - Exemplo: `user_form:submit` → on: → `run:` com `stdin` baseado nos dados do formulário.
  - [ ] Evento de script:
    - Exemplo: `script.complete` → ShantillyEvent → on: → `update_state`/atualização de viewport.
  - [ ] Evento de modal:
    - Exemplo: `modal.confirmed` → ShantillyEvent → on: → `run:` com segredos preenchidos.
  - [ ] Em todos os casos, reforçar:
    - Sem chamada direta a ScriptRunner/Modal Stack por componentes ou LayoutManager.

    - Qualquer atualização de estado relevante (além de state interno de componente) deve passar por `UpdateState`/fluxo declarativo.

## Testing (Expectativas funcionais para bmad-qa, derivadas desta story)

- Unit:
  - Testes de matching `ShantillyEvent` → `OnHandler.Event`.
  - Testes garantindo que apenas ações declarativas (RunAction, ModalRequest, UpdateState) são disparadas.
- Integration:
  - Cenário UI → EventManager → on: → ScriptRunner → EventManager → atualização de componente.
  - Cenário Modal JIT via on:.
- Governance:
  - Checks automatizados para garantir:
    - Ausência de handlers soltos em `internal/runtime/**` que ignorem EventManager/on:.
    - Uso consistente de ShantillyEvent como tipo de evento interno.

## Notas

- Esta story não define detalhes de parsing/execução do campo `When` (expressões); pode permanecer como string a ser interpretada em wave futura, desde que não encoraje lógica ad-hoc fora do fluxo declarativo.
- Implementação concreta será detalhada por bmad-architect e bmad-dev/bmad-master em arquivos de arquitetura e no módulo `internal/runtime/event`, mantendo este documento em nível de requisitos e rastreabilidade.
